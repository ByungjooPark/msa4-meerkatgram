# 비전공자를 위한 전체 흐름 가이드

이 문서는 개발 배경지식이 없어도 "이 프로그램이 대략 어떻게 동작하는지" 이해할 수 있도록 쉬운 비유와 함께 설명합니다.

## 0. 기본 그림: 이 서버는 무엇을 하는가

Meerkatgram은 사진과 글을 올리는 커뮤니티 서비스입니다. 이 저장소는 그중 **"뒷단(백엔드)"** 만 담당합니다.

- **프론트엔드(화면)**: 사용자가 실제로 보는 웹페이지. 버튼을 누르고 글자를 입력하는 부분. (다른 저장소, Vue라는 도구로 만듦)
- **백엔드(이 저장소)**: 화면 뒤에서 "로그인이 맞는지 확인", "게시글 목록을 데이터베이스에서 꺼내오기", "사진 파일 저장하기" 같은 실제 일을 처리하는 부분.

둘은 마치 **식당의 홀(프론트)과 주방(백엔드)** 처럼 분리되어 있고, "주문서"(HTTP 요청/JSON)를 주고받으며 소통합니다.

## 1. 레스토랑 비유로 보는 전체 구조

| 레스토랑 | 이 프로젝트 |
|---|---|
| 손님 | 웹/앱을 사용하는 사용자 |
| 주문서 | HTTP 요청 (예: "로그인해줘", "게시글 목록 줘") |
| 입구 안내원(신분증 검사) | Spring Security 필터 — 로그인한 사람인지 토큰(신분증)을 확인 |
| 홀 직원 (주문 받기) | Controller — 손님의 요청서를 받아 형식이 맞는지 확인하고 주방에 전달 |
| 주방장 (실제 요리) | Service — 실제 비즈니스 로직 처리 (예: 비밀번호가 맞는지 비교, 몇 페이지째 게시글을 꺼낼지 계산) |
| 창고 관리인 | Repository — 냉장고(데이터베이스)에서 재료를 꺼내고 넣는 역할 |
| 냉장고/창고 | Database (MySQL) — 실제 데이터가 저장되는 곳 |
| 서빙된 요리 | HTTP 응답(JSON) — 손님에게 돌아가는 결과 |

즉 요청 하나가 들어오면:

```
손님(요청) → 안내원(보안 검사) → 홀 직원(Controller) → 주방장(Service) → 창고 관리인(Repository) → 냉장고(DB)
                                                                                      │
손님(응답) ←──────────────────────────────────────────────────────────────────────────┘
```

## 2. "신분증(로그인 토큰)"이 있어야 들어갈 수 있는 곳

이 서비스는 모든 요청마다 "당신이 로그인한 사람이 맞습니까?"를 확인하지 않으면 곤란한 기능들(예: 게시글 상세 보기, 로그아웃 등)이 있습니다. 그런데 서버는 손님을 한 명씩 계속 기억하고 있지 않습니다(이걸 전문 용어로 "Stateless"라고 합니다).

대신 다음과 같은 방식을 씁니다.

1. 손님이 처음 로그인하면, 서버는 **두 개의 "신분증"** 을 발급합니다.
   - **출입증(Access Token)**: 유효기간이 짧고, 손님이 매 요청마다 직접 들고 다녀야 함(요청 헤더에 실어 보냄).
   - **재발급용 카드(Refresh Token)**: 유효기간이 길고, 브라우저의 쿠키(자동으로 관리되는 저장소)에 안전하게 보관됨. 출입증이 만료되면 이 카드로 새 출입증을 다시 받습니다.
2. 서버는 재발급용 카드의 사본을 데이터베이스에도 저장해두고, 나중에 손님이 재발급을 요청하면 "쿠키에 있는 카드"와 "DB에 저장된 카드"가 똑같은지 대조합니다. 다르면 위조/탈취로 간주하고 거부합니다.
3. 로그아웃하면 DB에 저장된 재발급용 카드를 지우고, 쿠키도 만료시켜서 더 이상 재발급이 불가능하게 만듭니다.

이 "신분증"의 정체가 바로 **JWT(JSON Web Token)** 라는 것으로, 사실은 서버만 알 수 있는 비밀키로 서명된 암호화된 문자열입니다. 위조하면 서명이 깨지기 때문에 서버가 바로 알아챌 수 있습니다.

## 3. 예시로 보는 실제 흐름 3가지

### (1) 로그인 흐름

1. 손님이 이메일/비밀번호를 입력하고 "로그인" 버튼 클릭 → 서버의 `/api/login`으로 요청서 전달.
2. 홀 직원(`AuthController`)이 요청서 형식(이메일 형식이 맞는지, 비밀번호가 비어있지 않은지)을 먼저 검사.
3. 주방장(`AuthService`)이 실제로:
   - 그 이메일로 가입한 손님이 있는지 창고(DB)에서 확인
   - 입력한 비밀번호를 암호화해서 저장된 비밀번호와 일치하는지 비교
   - 맞으면 출입증(Access Token) + 재발급용 카드(Refresh Token) 새로 생성
   - 재발급용 카드는 DB에도 저장, 쿠키에도 저장
4. 손님에게 "로그인 성공 + 출입증 + 내 정보"가 담긴 응답이 돌아감.

### (2) 게시글 목록 조회 흐름

1. 손님이 게시글 목록 화면을 열면 서버의 `/api/posts?page=1&limit=6` 요청.
2. 이 API는 신분증이 없어도 볼 수 있는(비로그인도 가능한) 공개 API입니다.
3. 주방장(`PostService`)이 "몇 번째 페이지의 몇 개를 가져올지" 계산하고, 창고 관리인(`PostQueryRepository`)에게 "삭제되지 않은 게시글을 최신순으로, 작성자 정보까지 같이" 가져오라고 지시.
4. 결과를 "전체 개수, 마지막 페이지 여부, 게시글 목록"으로 정리해서 응답.

### (3) 파일(이미지) 업로드 흐름

1. 손님이 프로필 사진 또는 게시글 사진을 선택해서 업로드.
2. 서버(`FileService`)가 확장자가 허용된 이미지 형식(`jpg`, `png` 등)인지 확인.
3. 원본 파일명 대신 "날짜_무작위값.확장자" 형태의 새 이름을 만들어서(예: `20260710_ab12cd34.png`) 서버 디스크에 저장.
4. 저장된 파일에 웹에서 접근할 수 있는 주소(URL)를 만들어 손님에게 돌려줌. 손님은 이 주소를 회원가입/게시글 작성 시 같이 제출합니다.

## 4. 무언가 잘못됐을 때 (에러 처리)

레스토랑에서 "품절입니다", "예약이 없으시네요" 같은 안내를 손님에게 통일된 방식으로 전달하듯, 이 서버도 어떤 에러든 항상 같은 모양으로 응답합니다.

```json
{
  "code": "E01",
  "message": "NOT_REGISTERED_ERROR",
  "data": null
}
```

- `code`: 무슨 문제인지 나타내는 짧은 코드(성공이면 `00`, 실패면 `E`로 시작하는 코드)
- `message`: 어떤 종류의 에러인지 설명
- `data`: 성공 시 실제 결과 데이터, 실패 시 부가 정보(있을 수도, 없을 수도 있음)

이렇게 **응답 형식을 하나로 통일**해두면, 화면(프론트엔드)을 만드는 사람이 "성공인지 실패인지, 실패라면 무슨 이유인지"를 매번 똑같은 방식으로 확인할 수 있어 개발이 쉬워집니다.

## 5. 자주 나오는 용어 쉽게 풀어보기

| 용어 | 쉬운 설명 |
|---|---|
| API | 프로그램끼리 대화하기 위한 "메뉴판". 어떤 요청을 보내면 어떤 응답이 오는지 정해진 약속 |
| REST API | 웹 주소(URL)와 요청 방식(GET/POST 등)의 조합으로 "무엇을, 어떻게" 할지 표현하는 API 스타일 |
| JSON | `{ "이름": "값" }` 형태로 데이터를 주고받는 텍스트 포맷. 사람도 읽을 수 있는 데이터 교환 형식 |
| DB(데이터베이스) | 회원정보, 게시글 등을 실제로 저장해두는 창고. 여기서는 MySQL이라는 제품을 사용 |
| Entity(엔티티) | DB의 표(테이블) 한 줄(row)을 자바 코드로 표현한 것. `User`, `Post` 클래스가 여기 해당 |
| DTO | Entity를 그대로 보여주면 비밀번호 같은 민감정보까지 노출될 수 있어서, "화면에 보여줄 데이터만 따로 골라 담는 상자". Request DTO(요청 상자), Response DTO(응답 상자)로 나뉨 |
| JWT | 로그인 상태를 증명하는 위조 방지 디지털 신분증 |
| 소프트 삭제(Soft Delete) | 데이터를 실제로 지우지 않고 "삭제됨" 표시(날짜)만 남겨서, 나중에라도 복구/추적할 수 있게 하는 방식. 이 프로젝트는 게시글/유저 모두 이 방식을 씁니다 |
| 트랜잭션(Transaction) | "전부 성공하거나 전부 취소"를 보장하는 안전장치. 예를 들어 로그인 처리 중간에 문제가 생기면, 절반만 처리된 상태로 남지 않도록 전체를 되돌립니다 |
